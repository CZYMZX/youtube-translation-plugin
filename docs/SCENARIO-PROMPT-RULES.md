## 一、三条规则的落点

| 缺口 | 场景 | 条款位置 | 加了什么 | 为什么这么写 |
|---|---|---|---|---|
| 1. 括注原文 | vtuber | 新增第 10 条 | 专名只出中文译名；禁括号原文 / 罗马字 / 英文补充；同批同专名同一译法；术语表已给出的译名直接用作准，不再另加原文 | 旧 prompt 只在 general 侧有「不加括注」，vtuber 侧无约束 → 切片里出现「加尔干达（Gargander）」。反例直接写进条款（形如 `X（Y）` 一律不允许），比抽象禁止更可执行；「同一批」限定与缓存批次粒度一致；「术语表已给出的直接用」避免绕过术语注入 |
| 2. AI 腔禁用清单 | vtuber / general | vtuber 新增第 11 条、general 新增第 5 条 | 列出禁用套话：值得注意的是 / 总而言之 / 让我们一起 / 首先…其次 / 不难发现 / 综上所述 / 众所周知 / 由此可见；禁补连词、补主语、补解释 | 两个场景各写一份（场景包是独立文案，不做跨包引用）；措辞统一，便于日后同步改。关键是把禁止写成**条件式**——「原文没有的意思不做补充…原文确有此意时按口语直译」：清单里「首先…其次」「让我们一起」在讲解类原文中确有可能出现，若写成无条件禁用会诱导漏译，条件式同时保住「不增补」和「不漏译」 |
| 3. 自适应分层 | general | 第 3 条**改写（增量）** | 原「访谈类内容保留说话人的礼貌层级」原样保留为访谈层；新增讲解层（书面化）、闲聊层（口语化）；补三条面的判定线索；补「同一批内保持同一层级，不逐句来回跳」 | 线索全部取自本批已送入的句子（说话人交替 / 句末です・ます / 句长 / 术语与数字单位密度 / 常体だ・よ・じゃん / 口癖语气词），**不引入新的模型调用、不要求额外视频元信息**；原第 1、2、4 条一字未动，第 3 条主体（敬语层级）保留 ⇒ 属增量而非重写；「同一批内不来回跳」对应「方言/语气逐批漂移」的同类问题 |

三条规则的共同前提（沿用领域准则）：整句翻译、不逐词、不增补原文没有的信息、不加解释性连接词、语气服从场景而非客服体。

## 5.3 缓存指纹：s1 → s2（覆盖整段静态骨架）

- 旧（s1，无前缀）：`scenarioId#hash(场景包 prompt)` —— 公共层文案改了**不会**失效，等于白改。
- 新（s2）：`s2.scenarioId#hash(buildPromptSkeleton(...))`，骨架 = 场景层 + 公共层 + 选项层 + 推理层 + 输出契约。
- 骨架**刻意不含**按批变化的术语块：若纳入，同一句在不同批次会算出不同的键、缓存永久不命中。
- 完整键形态：`service:model:s2.scenarioId#skeletonHash:reasoning:targetLang:text[:glossaryTag]`。

失效影响面（一次性，不是长期）：

| 对象 | 是否失效 | 原因 |
|---|---|---|
| 全部内置场景（vtuber / general） | 失效 | 场景包文案变 + 指纹口径变 |
| 三个占位场景（science / music / gaming） | 失效 | 回落 general 文案，同样吃新指纹 |
| 用户上传的自定义场景包 | **失效**（上轮不会） | 指纹从「只 hash 场景包」改为 hash 整段骨架 |
| 切换 `glossaryAnnotation` / `asrCorrection` | 失效 | 选项进骨架 ⇒ 进指纹 |
| 术语库标签（`g1.…`） | 不受影响 | 本轮未改术语数据与匹配规则 |
| `service=google` 的缓存 | 也会失效（重取一次） | Google 通道不用 system prompt，选项对译文无影响，但键相同口径；代价仅一次免费重取 |

用户代价：升级后首次观看时，凡是命中旧键的句子会重新请求一次模型（= 按新规则重新生成），之后照常命中；
旧条目不再被命中，由 IndexedDB 30 天 TTL 自然淘汰，想立刻回收可在高级设置「清空翻译缓存」。

## 5.4 两种 ASR 模式对 token 的实际影响（如实说明）

用户原假设是「纠错授权收紧会多消耗 token」。实测**不成立**：

- prompt 侧：`normal` 档 76 字 / `strict` 档 114 字，差 38 字符 ≈ 20~25 token，**每次 API 请求**一次（不是每句）；
  一批 8 句摊薄后 < 5 token/句，相对 1500 字骨架（≈800~1000 token）是 2~3% 的波动。
- 生成侧：`strict` 没有要求额外步骤（不要求先判后改、不要求输出判断理由、不要求思维链），因此**不产生额外输出 token**；
  它甚至会因为「不确定就保留原文」而少改写，输出可能更短。
- 真正会显著涨 token 的做法是「先逐句判断是否误转、再改写」的两步推理，本轮刻意没这么做。
- 结论：两种模式 token 差 ≈ 噪声级；选 `strict` 买到的是「更少误改事实」，不是「更多 token 换质量」。

对比 `glossaryAnnotation`：off 148 字 → on 264 字（+116 字符 ≈ 60~80 token/请求），且输出侧每个专名多出 2~N 字
（同批每专名首次出现括注一次）。**这个选项才是真正会增加 token 的那个**，但增量同样很小。

## 6.1 问题

`glossaryAnnotation = 'on'` 要求输出「中文译名（日文原文）」。但术语表里有条目的 zh 自带括号注释：

```
术语块：- スパチャ → SC（醒目留言）（用语）
按旧规则：SC（醒目留言）（スパチャ）      ← 双层括号，观感差
```

## 6.2 改法（`utils/translator.ts#buildAnnotationRule('on')` 第三段）

只在 on 档追加一段，三条约束写在一起：

> 译名自带括号时不得叠成两层：中文译名本身已带全角圆括号注释的（如「SC（醒目留言）」），只取括号前的主词再补原文，
> 写成「SC（スパチャ）」，括号里原有的中文解释丢掉（那是给中文读者的说明，不属于译名）。只认全角圆括号（），
> 半角括号、「」『』、方括号都不算注释、不据此拆分。括号内若是不可省略的限定（同名区分、版本或团体归属，
> 如人名「佐藤（声优）」），整条译名保留原样、不再追加原文。怎么分：去掉括号后主词在本批里仍能唯一指向该专名＝解释，
> 可拆；指代会变歧义＝限定，保留。

体量：off 148 字不变 / on 264 → 500 字（+236 字，≈130 token，**每次请求一次**、按批摊薄，不进输出）。

## 6.3 三个边界的处理

| 边界 | 处理 | 为什么 |
|---|---|---|
| 括号必须是**全角中文圆括号（）** | 只认 `（）`；半角 `()`、「」『』、方括号一律不视为注释、不据此拆分 | 译名里的注释是中文排版习惯（全角）；把半角也算进去会误伤原文里本来就有的半角括号与英文缩写，拆出来的「主词」不可控 |
| zh 本身是**拉丁字母**（AZKi / IRyS / ReGLOSS / hololive DEV_IS） | 去重条款根本不触发（它们不带全角括号），继续按上一轮「只写一次原名」处理，不会变成 `AZKi（AZKi）` | 去重的前提是「括号前有主词可留」；拉丁字母名整体就是译名，没有可剥的注释层。规则顺序上「只写一次」在前、去重在后，两者不冲突 |
| 括号内是**必要限定**（同名区分 / 版本、团体归属） | 整条译名保留原样、**不再追加原文**（宁少一次括注，也不叠括号、不拆坏指代） | 判定标准（可执行、不依赖外部知识）：**去掉括号后主词在本批上下文里是否仍能唯一指向该专名** —— 能 ⇒ 括号内是给读者的解释（如「醒目留言」解释 SC 是什么），可拆；不能 ⇒ 括号内是限定（如「佐藤（声优）」区分同名），保留。拿不准按「限定」处理（保守侧：保持可读，少一次括注） |

## 6.4 缓存影响（比预想的小：只有 on 档失效）

| 对象 | 是否失效 | 说明 |
|---|---|---|
| `glossaryAnnotation = 'on'` 的用户 | **失效** | on 段文案进静态骨架 ⇒ 指纹变：`hashPrompt(骨架)` 1hd1bh6 → 1qz5v |

| 自定义场景包 | 跟随所在档位 | 同上，取决于该用户选的是 off 还是 on |

## 6.6 本轮遗留风险

1. **括号内是「限定型」的条目在 on 档拿不到原文**：按 6.3 第三条保留原样不追加，等于该处少一次括注。
   真正解法是术语库分「译名 / 短译名」两个字段（`glossary-keeper`），prompt 侧只能做取舍。
2. **「解释 vs 限定」最终靠模型判断**：判定标准已写成「主词是否仍唯一指向」，但同一批上下文不足时模型仍可能选错。
   错拆（把限定当解释）比叠括号更难看，所以默认口径是「拿不准就保留」。
3. **去重不递归**：只处理一层括号（`A（B）`），`A（B（C））` 这种嵌套不在约定内（术语库目前无此形态）。
4. **术语块行尾的分类标签也是括号**：`buildGlossaryPromptBlock` 输出的是 `- スパチャ → SC（醒目留言）（用语）`，
   行内有两个全角括号 —— 「（用语）」是分类标签、不是译名，但去重条款只按「译名自带的括号」判断，模型需自行区分。
   本轮不加条款（避免又一条公共约束），根治办法是 glossary 侧把分类标签改成行内前缀（如 `[用语] - ja → zh`），属 `glossary-keeper`。
5. **未跑真实模型**：以上全是静态守卫，`SC（醒目留言）` 的最终吐字仍需接模型抽检（建议抽 hololive 打赏切片）。
6. **第六节的 v0.4.4 是工作轮次标签**，不是 `package.json` 版本号（仍 0.4.0）。
