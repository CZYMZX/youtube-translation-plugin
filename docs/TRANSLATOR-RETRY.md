# 失败句局部重试（翻译链路 · 任务二）

需求原话：「检测翻译失败的语句，对其前后语句一同分析，尽量减少整轨同译，减少 token 消耗。」

本轮**只改翻译失败后的补译路径**，不动场景 / 公共 / 选项层的提示词文案，因此缓存指纹不变、用户已翻内容不失效。
未改版本号、未构建产物、未动 `entrypoints/*`、未提交。

## 一、改动位置与流程

| 文件 | 改了什么 |
|---|---|
| `utils/translator.ts` | ①新增失败句重试基础设施（`retryFailedSentences` / `buildRetryItem` / `mapRawItemsToSlots` / `parseRetrySingle` / `RETRY_CONTRACT`）；②把「发一次请求」和「失败后怎么补」拆成两层（`callOpenAiRaw` / `callGeminiRaw` 只做一次往返，`translateWithLlmChannel` 做编排）；③三个通道统一返回 `SliceResult`（`null` = 该句最终失败）；④`commitBatch` / 落库只写成功项；⑤新增 `translateSentenceBatchDetailed()`，`translateSentenceBatch()` 保持原签名做薄封装 |
| `test/test-retry.js` | 新增 59 条断言（假通道，不联网） |
| `package.json` | `test` 脚本串入 `test-retry.js`（仅此一行） |
| `docs/TRANSLATOR-RETRY.md` | 本文 |

未改：`utils/segmenter.ts`、`utils/glossary.ts`、`utils/packs.ts`、`utils/db-cache.ts`、`utils/translation-queue.ts`、`entrypoints/*`。

流程（LLM 通道：openai / deepseek / gemini）：

```
未命中缓存的 N 句
   └─ 首轮：一次请求送全部 N 句（与旧行为一致，不加请求）
        └─ 按 id 归位 → 缺条目 / 译文为空 / 响应不是合法 JSON 数组 ⇒ 该句 failed
             ├─ 成功句：立刻落库 + 写缓存（内存 + IndexedDB）
             └─ 失败句：逐句单独发一次请求
                   payload = [{ id:0, text:失败句, context_before:前一句, context_after:后一句 }]
                   system = 静态骨架 + 【本次只补一句译文】契约
                   只认 id=0 那一条译文 → 成功即落库写缓存
                   失败 → 退避后第 2 次（上限 MAX_SENTENCE_RETRIES=2）
                   2 次都失败 → 放弃，记 failed，填占位符，**不写缓存**，本批照常返回
```

Google 免费通道同样走「首轮 → 失败句逐句重试（≤2 次）」，但该通道没有 system prompt、无法利用前后文，重试只借用「上限 + 退避 + 时间预算」这套护栏。

## 二、失败判定的现状与补强

**改前**（`translateWithOpenAICompatible` / `translateWithGemini`）：
- 「条目缺失 / 译文为空」**有检测，但代价是整批作废**：`missing.length > 0` 直接 `throw new Error('模型返回条目不完整…')`，一次性丢掉本批**已经翻好的句子**，然后走外层 catch → 降级 Google 重翻整批，或整批报错占位。
- 「响应不是合法 JSON」直接抛错，同样整批作废。
- Google 通道：合并请求按行数判断，行数不匹配就逐句重取；**单句仍失败时把 `[翻译失败: …]` 当译文交给 `commitBatch` 写进了缓存**（下次播放直接命中一条假译文），这是本轮修掉的真实 bug。

**改后**（逐句级判定，四类都只影响该句）：

| 现象 | 归因 | 处理 |
|---|---|---|
| 返回里没有该 id，或 `translation` 为空/空白 | 句级失败 | 该句进逐句重试，其余句照常落库 |
| 响应拿到但不是合法 JSON 数组（`parseModelJsonArray` → null） | 句级失败（整批都算） | 整批进逐句重试，**不重发整批** |
| HTTP 4xx/5xx、网络中断、超时 | 传输级失败 | 不在内容层重放：`callWithRetry` 已在网络层退避重试过 2 次，仍失败则上抛，走既有「noFallback 抛错 / 降级 Google」路径 |
| 单句重试期间再遇到传输级故障 | 端点级 | `retryFailedSentences` 立刻停手（`aborted`），不再对剩余句空转 |

失败掩码 `failed` 通过 `translateSentenceBatchDetailed()` 暴露给调用方；供 UI 用的 `translateSentenceBatch` 签名不变。

**一处刻意的行为变化**：句级失败不再自动降级到 Google。旧逻辑是「整批缺条目 → 抛错 → 整批走 Google」，
新逻辑是「失败句重试 2 次 → 仍失败就留占位、不写缓存、下次播放再试」。理由：降级会把一句模型失败变成
整批机翻质量（且要重付整批 token），而用户要的是「只补那一句」。
传输级故障（网络 / HTTP）仍然保留原有的 Google 降级路径，语义不变。

## 三、token 对比估算

估算口径（非实测 API）：静态骨架 ≈ 1500 字 ≈ 900 token；单句原文 25 字 ≈ 18 token；单句译文 30 字 ≈ 25 token；
一批 8 句 ⇒ 骨架 900 + 8×18 + 8×25 ≈ **1,244 token/次请求**；单句补译契约 ≈ 120 字 ≈ 75 token。
一条 20 分钟切片按 300 句算，分批 8 句 ⇒ 38 批。

| 方案 | 一句失败时的额外消耗 | 备注 |
|---|---|---|
| 整轨重译 | 38 × 1,244 ≈ **47,000 token** | 最坏情况的老路径（整批抛错后重翻整轨） |
| 整批重发（1 批） | 1,244 token | 已成功的 7 句再付一次 |
| **本方案（局部重试，1 次成功）** | 900 + 18 + 36（上下文两句）+ 75（契约）+ 25 ≈ **1,054 token** | 相对整轨重译 **−98%**，相对整批重发 **−15%** |
| 本方案（2 次都失败） | ≈ **2,100 token** | 相对整批重发 **+70%**，换来「不重翻已成功的句子」与更小漂移 |

量级结论：**与「整轨重译」差两个数量级（约 2%），与「整批重发」在同一量级（±15%~+70%）**。

如实说明局部重试的成本结构：固定成本是骨架（900），不是失败句本身。因此：
- 失败句数 ≤ 1 时，局部重试比整批重发更省；
- 失败句数 ≥ 2 时，局部重试的 token 会比「整批重发一次」多（每多一句多付一次骨架）；
- 但输出侧永远只产出失败句（1 句 vs 8 句），且**已成功句一个字都不会重翻**，这是「减少整轨同译」的实质收益。
- 若某端点长期大批量缺条目（例如一次 8 句缺 5 句），真正的修法是换模型/换端点或修输出契约，不是靠重试省 token；本轮按需求「只重试失败句」执行，不自动退化成整批重发。

护栏：单句最多重试 2 次（首次之外），重试总预算 `RETRY_TIME_BUDGET_MS = 8000`，超预算立即放弃剩余句；
遇端点级故障立即停手 —— 这三条一起保证「最坏情况」也不会变成 N 句 × 2 轮的空请求。

## 四、最大的正确性风险：失败句与上下文句串写

风险场景：重试请求里同时存在「失败句 + 前后两句原文」，模型可能返回 3 条译文；一旦按返回顺序回填，就会把上下文句的译文写进失败句，或把 3 条挤进 1 个槽位。

四道闸（缺一不可，均有单测）：

1. **上下文与待译句在 payload 里是不同字段**：`text` 是唯一要求翻译的字段，`context_before` / `context_after` 只是邻居原文；契约明确写「不得翻译、不得输出、不得并入译文」。
2. **重试请求只要求一条**：`RETRY_CONTRACT` 把输出钉成 `[{"id":0,...}]` 单元素数组；上下文句**没有 id**，模型无从按 id 输出它们。
3. **解析只认 id=0，且必须恰好一条**（`parseRetrySingle`）：模型多吐的 id=1/2 一律丢弃；吐两条 id=0（无法判断哪条对应失败句）直接判失败、宁可再试一次也不猜。
4. **回填按「失败下标」而不是模型给的 id**：`retryFailedSentences` 用 `filled: Map<句下标, 译文>` 回填，`idx` 来自首轮自己的失败掩码，模型返回的任何 id 都不参与定位。

首轮的归位同样加了闸（`mapRawItemsToSlots`）：只认 `0..N-1` 的 id，越界 id（如模型返回 `id:99`）直接丢弃，重复 id 后者覆盖前者，空译文进 `null` 槽位而不是串到邻句。

另一处易混点：**上下文句不参与术语匹配**（重试时 `translatable = [失败句]`），避免为不产出的句子注入术语块、也避免术语块被上下文里的专名带偏。

## 五、缓存影响

- **缓存键完全没变**：`service:model:s2.场景id#骨架hash:reasoning:targetLang:text[:glossaryTag]`。
  `RETRY_CONTRACT` 与上下文只出现在**重试请求**里，不进 `buildPromptSkeleton()`，因此**不产生一次性全量失效**（有单测断言骨架不含契约）。
- 成功即写缓存（内存 + IndexedDB），失败一律不写：不写空值、不写 `[翻译失败: …]` 占位、也不拿原文顶替。
- 修掉的旧 bug：Google 通道单句失败时曾把 `[翻译失败: …]` 写进缓存；这类历史脏条目仍按 IndexedDB 30 天 TTL 自然淘汰，想立刻清可在高级设置「清空翻译缓存」。
- 用户需要做什么：**什么都不用做**。下次播放失败句会重新尝试（因为没被缓存），命中就再也不同请求。

## 八、遗留问题与风险

1. **批首/批尾只有单侧上下文**：`*_BATCH` 消息只带本批 8 句，第一批的第一句与最后一句拿不到批外邻居。要补齐需让 background/内容脚本透传 ±1 句窗口（属协议层，需改 `entrypoints/*`，本轮禁改）。
2. **队列超时与重试预算可能叠加**：队列 `requestTimeoutMs` 默认 20s，慢端点下「首轮 20s + 重试预算 8s」可能超过它，队列会按超时把整批重新置 idle（= 变相整批重译）。本轮已把重试预算压到 8s 并加端点级故障立刻停手；根治需让队列超时按批大小/是否在重试自适应，或让 background 透传进度。
3. **占位符仍会显示**：失败句最终填 `[翻译失败: …]`，队列收到的是普通字符串，`status` 仍为 `done`（因为它拿不到 `failed` 掩码）。要在 UI 上区分「失败」需要把 `TranslateBatchDetail.failed` 透传到 `TRANSLATE_BATCH` 响应里 —— 属协议 + UI 层，本轮未做。
4. **未跑真实模型**：所有断言基于假通道，真实端点的「缺条目」概率、上下文是否真的改善指代/语气，仍需接模型抽检（建议在 `isAi` 全篇精翻路径上抽 1 条轨道对照）。
5. **`SliceResult.errors` 只用于诊断**：目前只喂给占位符文案与 `failed` 掩码，没有上报到设置页；若要做「失败句统计」需另开口径。
6. **temperature 仍固定 0.3**：重试沿用同一温度，未分场景/分重试调温（端点兼容性属他人范围）。
7. **整批 0 条可用译文时的代价**：若某端点对一批 8 句全都不返回条目，本方案会先发 8×2 = 16 次单句重试再放弃（约 17k token），
   比旧的「整批抛错 → Google 降级」更费。判断：这种「整批契约失效」的场景应换模型/端点或修输出契约，
   而不是靠重试；若后续确认常见，可加一条「整批 0 命中时直接走上层降级」的短路（本轮按需求「只重试失败句」未加）。
