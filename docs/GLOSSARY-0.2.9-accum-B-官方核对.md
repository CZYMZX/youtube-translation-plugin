# MC 术语库官方核对报告（v0.3.1）

> 背景：v0.3.0 的 74 条 MC 术语因当时 wiki 全部不可达，是依据检索结果人工整理的。网络恢复后，本轮改用
> **Minecraft 官方语言文件**做逐条机器核对，并整体重建该术语库。

---

## 一、数据源（权威、可复现）

Minecraft Java Edition **1.21.4** 官方语言文件，三语同源同 key：

```
assets/minecraft/lang/ja_jp.json   （日文，546 KB）
assets/minecraft/lang/zh_cn.json   （简体中文，449 KB）
assets/minecraft/lang/en_us.json   （英文，442 KB）
```

镜像地址（jsDelivr）：

```
https://cdn.jsdelivr.net/gh/InventivetalentDev/minecraft-assets@1.21.4/assets/minecraft/lang/{ja_jp,zh_cn,en_us}.json
```

**为什么用语言文件而不是 wiki 页面**：语言文件是游戏内文本的唯一来源，键名（如 `entity.minecraft.sheep`）
与译文一一对应，可保证「日文原名 → 官方中文译名」是逐字一致的官方口径；wiki 页面是二手整理，且会随版本漂移。

1. 下载 1.21.4 三语语言文件；
2. 取 v0.3.0 术语库的 74 条 `[ja, zh, en]` 三元组；
3. 用**日文值反查 key**（同一 key 下取中文值），与库中 zh 比对；
4. 对反查失败的条目，按语义定位官方 key 后人工确认。

## 七、复测中发现的匹配缺陷（已修复）

旧匹配器是纯子串判断（`haystack.includes(key)`，且要求日文 ≥2 字），
换上官方 165 条后暴露出两个真实问题：

### 缺陷 1：8 个单字术语永不生效

`土 / 石 / 砂 / 氷 / 弓 / 矢 / 盾 / 毒` 因为“≥2 字”规则被直接跳过——列表里看得见，翻译时永远不会注入。

**修复**：单字汉字改为**边界匹配**——左右邻接都不是汉字才算命中。假名（助词）视为合法边界，所以
`土を掘る` 能命中，而 `土曜日` / `宝石` / `砂漠` / `氷点下` / `弓道` 不会误命中。
实测：6/6 该命中的都命中，5/5 不该命中的都拦住。

### 缺陷 2：「修繕」在日常生活句里被当成附魔

`修繕` 既是官方附魔名（Mending → 经验修补），也是日语常用词（修补）。
实测 `この家、修繕しないとな。` 加上术语库后译成 **“这栋房子得弄个经验修补才行啊”**，明显跑偏。

**修复**：引入 `needsContext` 标记 + **按句**语境判定——同句命中 ≥2 条术语才算游戏语境。
（第一版按整批判定，被同批其他句子的正常术语“救活”，仍会出错；改为逐句后修复。）

> **v0.4.2 补记（此处为历史记录，现行口径见 `GLOSSARY-0.2.8.md` 顶部与 `utils/glossary.ts`）**：
> 上述「同句命中 ≥2 条」把门控词自己也数了进去，门槛又正好是 2，于是两个门控词同句即互相救活：
> `幸運なことに、この家を修繕しないとな` → `幸運` + `修繕` 双双注入；`このAPIのトークンが切れて、彼の推論も止まった`
> → `トークン` + `推論` 双双注入。现改为**语境证据只数非门控术语**，门槛「≥1 条普通术语」，
> 并 bump `GLOSSARY_MATCHER_REVISION` 1→2 以作废旧缓存。

修复后同一句：OFF 与 ON 输出完全一致（“这房子得修修了啊”），而 MC 语境句仍正常注入（`幸運` 在
`幸運エンチャントつけたい、ダイヤモンドのツルハシに` 中照常生效）。

## 八、实译验证（端点恢复后补跑）

模型：`gemini-3.1-flash-lite`（用户本机 8045 端点），术语库 MC 包 ON/OFF 对照：

| 原文 | OFF（无术语库） | ON（有术语库） |
|---|---|---|
| 移動速度上昇のポーションある？ | 有加移动速度的药水吗？ | **有迅捷药水吗？** |
| このツルハシ、ダメージ増加とシルクタッチが付いてるんだよ。 | 附魔了伤害增加和精准采集哦 | **附带了锋利和精准采集哦** |
| あ、ヒツジいた！羊毛集めよ。 | 有只**羊**！ | 有只**绵羊**！ |
| この家、修繕しないとな。 | 这房子得修修了啊 | 这房子得修修了啊（✅ 未被污染） |

结论：官方口径在**口语直译与官方译名分歧处**收益最大（`移动速度上昇→迅捷`、`ダメージ増加→锋利`），
在模型已知的常见词上无差异（`苦力怕/火把/末地`），在跨语境高频词上已能正确避让。

## 九、AI 术语库的维基核对（走代理）

### 9.1 网络：直连不通，代理可用

| 路径 | ja/zh.wikipedia |
|---|---|
| 直连（curl / 浏览器扩展） | ❌ 000 / 错误页 |
| 系统代理 `127.0.0.1:7897` | ✅ 200 |

本机 Clash 监听 7897（`google/generate_204` 返回 204）；扩展注入的页面走系统网络、不吃这个代理，
所以“浏览器里打不开维基”和“脚本能抓维基”同时成立，并不矛盾。

### 9.2 核对方法（维基 API，非页面抓取）

1. 取日文条目 → 读 `prop=langlinks&lllang=zh`，得到中文对应条目名；
2. 反向再验：把 35 个中文译名一次性丢给中文维基 `action=query`，看条目是否存在、是否被重定向。

结果：**28/35 在中文维基有对应条目**（其余为「生成式 AI / 提示词 / 提示工程 / 多模态 / 检索增强生成 / 图像生成 / 无监督学习」这类
维基用词不同或未单独立条，不代表译名有误）。

### 9.3 发现的问题与处理

| 问题 | 依据 | 处理 |
|---|---|---|
| `学習 → 训练` 过宽 | 中文跨语言链接指向「学习」；实测「学習塾」会被误伤 | **移除**，替换为 `事前学習 → 预训练`（语义唯一） |
| `トークン → 词元` 跨领域 | 认证场景 token = 令牌，非“词元” | 标记 `needsContext` |
| `推論 → 推理` 跨领域 | 逻辑学「推論」也是推理，但非 AI 语境无需锁定 | 标记 `needsContext` |
| `エージェント → 智能体` 跨领域 | 一般义为“代理人/代理” | 标记 `needsContext` |

### 9.4 保留业界用法（与维基标题不同，非错误）

| 术语 | 本库 | 中文维基标题 | 说明 |
|---|---|---|---|
| 大規模言語モデル | 大语言模型 | 大型语言模型 | 两者通用，业界更常用“大语言模型” |
| プロンプトエンジニアリング | 提示词工程 | 提示工程 | 两者通用 |
| エージェント | 智能体 | 智能代理 | AI 语境下“智能体”更常见 |
| 生成AI | 生成式 AI | 生成式人工智能 | 字幕场景求短，保留缩写 |

### 9.5 AI 包实测（语境门控）

```
AI 语境：大規模言語モデルの事前学習 → 大语言模型 + 预训练 ✓
        トークン数がコンテキストウィンドウを超えてる → 词元 + 上下文窗口 ✓
日常句：今日は学習塾に行ってきた → 无命中 ✓
        このAPIのトークンが切れてる → 无命中（不误判为词元）✓
        彼は論理的に推論した → 无命中 ✓
```

## 十、遗留

- 术语库是**词表约束**，不保证模型 100% 遵守；实际效果取决于模型对 prompt 的服从度。
- 语境门控的取舍：`修繕つきのツルハシ欲しい` 这类「只有一个 MC 词」的短句，`修繕` 会被判为非语境而不注入
  ——宁可漏注，也不让日常句被强塞游戏译名。
- AI 包仍有 7 条在中文维基无独立条目，属维基收录粒度问题，如需更权威口径可再查「术语在线」（termonline.cn，
  已确认可达，但其检索为 SPA，需浏览器交互）。
