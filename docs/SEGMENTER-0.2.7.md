## 一、问题

断句单元 = 翻译单元 = 显示单元，三者绑死在**源语言**断句上。源语日语（SOV）→ 目标语中文（SVO）时：
1. **词中切断**：硬上限切点落进活用词内部（「配信つけ | たんやけど」）；
2. **悬空宾语行**：以格助词结尾的行单独成句（「ガルガンダーを。」）；
3. **行级 ASR 不可切**：整行 76 字作为单 token 进入引擎，任何规则都无法在行内落刀。

逐行译文因此割裂（详见下文对照）。

## 二、修复（utils/segmenter.ts）

| # | 改动 | 说明 |
|---|---|---|
| A | **守卫 A·防劈词回退（双向）** | ① 下一 token 为 ≤2 字纯平假名且非已知话轮词 ⇒ 接续形态；② 当前组末 token 为 ≤2 字纯平假名且末字非终止助词（ね/よ/な/か…）⇒ 谓语未完成（覆盖「た」+「ん」逐字流）。多字 token 走前缀表（けど/ので/たら…）+ 完整词豁免（たぶん/やっぱ…） |
| B | **守卫 B·悬空助词防断** | 组末以格助词（を/が/に/は/も/で/と/へ/や）收尾时不切；下一 token 是合法新句开头（じゃあ/はい…）除外 |
| C | **规则 2 分级** | 超长停顿（≥max(2×阈值,800ms)）受守卫约束（词中换气不劈词）；**极端停顿仍无条件切**（33 秒级静音防吞句的初衷不变）。极端阈值实际取 `max(5s, 3×超长停顿阈值)`：默认停顿阈值 450ms 时正好是 **5s**，用户把停顿阈值调到 >833ms 时该线会高于 5s（口径见遗留 4） |
| D | **安全阀** | 时长/长度达 2×上限时无视守卫强制切断，防无限吞句（合并 pass 无额外长度上限，靠这个 2× 天花板加单个 token 容差兜底，测试 19 允许 ≤64 字） |
| E | **行级 ASR 顿号细分** | token 文本 >40 字且含顿号/逗号时，在解析层按「、，,」子拆分（时间按字符比例分配），行级轨从此可切 |
| F | **句首伪影清理** | polishSentenceText 剥离句首「、，,」 |

不受守卫约束（有意保留）：规则 1 源标点（忠实原声，如说话人自我修正「ガルガンダーを。」）。

## 五、遗留

1. 「美味しい | パンがあるの」属**合法但次优**切点——需要 D 方案（译文语序感知切点偏好/词典）进一步优化；
2. 「パパって食べれるパン」为 ASR 转写错误（原话应为「ぱぱっと」＝快速地），非断句问题；
3. 「ガルガンダーを。」为说话人自我修正，源标点忠实保留；
4. **极端停顿阈值的上限依赖用户设置（待拍板）**：代码取 `max(5s, 3×超长停顿阈值)`，默认 450ms 停顿阈值下等于 5s，但用户把停顿阈值拉到 833ms 以上时，无条件切分线会升到 5s 以上（最大 7.2s）。若「≥5s 一律无条件切」要作为不随设置漂移的硬线，需改成 `max(5s, 超长停顿阈值)` 或固定 5s——属行为改动，未执行。

5. **超长句（>10s）根因补充（2026-11-06 实测，未改，不属噪声过滤范围）**：`payload-ja.txt` 全轨 195 个 >7.4s 句中，61 句句内含 ≥800ms 空档，这部分只能由后处理「短碎片合并」形成（该 pass 无时长/长度累计上限）；但关掉合并后仍有 176 句 >7.4s、最长 14.28s，说明主因不在合并 pass，而在断句主循环——守卫 A 把「≤2 字纯平假名 token」一律当作接续形态，单字/逐字粒度 ASR 流下几乎恒真，使规则 2b/3/4/5 被持续延后，实际只由 2× 时长天花板（13s）兜底；而该天花板只在 token 边界检查，末 token 自身时间较长时会溢出到 13s 以上（实测 11 句 >13s，最长 14.35s，其末 token 占 2.0s）。

### 7.1 复现与根因（`payload-ja.txt`，20740 tokens / 4017 句）

| 指标 | 值 |
|---|---|
| >7.4s | 195（4.9%） |
| >13s（2× 时长天花板） | 15 |
| 最长句 | 14.35s（60 字） |
| 极短句（实字 ≤2） | 437 |

实测三条成因，**只有前两条在方案A/B 的射程内**：

1. **守卫 A 对单字假名恒真，把长停顿一起拦下**：排第 1 的 14.35s 句内有一个 **4241ms** 空档（`え` `、` `な` …），规则 2b（≥900ms 硬切）本应在此落刀，但下一 token 是 `な`（≤2 字纯平假名）⇒ 判为接续 ⇒ 不切。该组最终由规则 3（6.5s）在 7.67s 处切断。
2. **2× 天花板只在「并入后」检查，末 token 完全不过检查**：突破 13s 的那个 token 已被吞进本句（末 token 连 `if (!nextToken)` 早退都跳过检查），溢出量 = 该 token 自身时长。
3. **短碎片合并 pass 无任何时长/长度上限**（A/B 都没碰）：上述 7.67s 组因「无终止标点 + 碎片规则」被并入后一句 6.68s ⇒ **7.67 + 6.68 = 14.35s**。关掉合并时主循环只给 7.67s（`mergeShortFragments:false` 实测）。量化（`scripts/compare-long-sentence.ts` 的「诊断」段）：merge **on** 时 195 个 >7.4s 句里 **118 句句内含 ≥800ms 空档（29 句含 ≥5s 空档）**；merge **off** 后仍有 **176 句** >7.4s、最长 **14.28s** ⇒ 合并 pass 解释了其中 19 句与最长句的尾巴，但**不是全部**，其余来自成因 1（守卫拦长停顿）与成因 2（末 token 溢出）。

**② 20445.92s ~ 20460.20s（14.28s / 9 字）**

**③ 5300.09s ~ 5314.20s（14.11s / 26 字）**

A     12.07s ｜ 3 体もいるのですが、えっと、えとライトを使って。 ＋ 12.36s ｜ も倒せず困っております。

### 8.1 实现（`utils/segmenter.ts` 后处理 1）

合并 pass 过去只在「碎片 + 相邻句」两个条件上决策，**没有任何累计时长/长度上限**，于是「7.67s 碎片 + 6.68s 句」被缝成 14.35s。现在加一道最外层闸门：

```ts
// 上限直接取自主循环对单句的同一组上限，不新增硬编码常量
const mergeCeilingDurationMs = maxDurationMs;               // 跟随用户设置，默认 6500
const mergeCeilingUnits = unitHardLimit;                    // CJK 按字 = maxCharsPerSentence（默认 28）
                                                            // 拉丁按词 = maxWordsPerSentence（默认 16）

fitsMergeCeiling(headTokens, tailTokens, start, end)         // 合并后时长 <= 上限 且 长度 <= 上限
```

四条行为约束（逐条对应用户要求）：

| 要求 | 实现 |
|---|---|
| 合并后不得超 `maxDurationMs` / 字数上限 | `fitsMergeCeiling` 同时校验时长与长度，任一超限即不合并 |
| 上限跟随用户设置 | 直接读 `settings.maxDurationMs` / `maxCharsPerSentence`（CJK）/ `maxWordsPerSentence`（拉丁），无写死常量 |
| 是最外层闸门，不改守卫 A/B 判定 | 闸门只出现在合并 pass，主循环守卫 A/B 代码零改动（测试 22e 复验「つけ/たんやけど」仍不劈） |
| 拒绝时不产生新碎片、不丢内容 | 拒绝后 `cur` 与 `next` **各自保留为独立句**（`merged.push(cur)`），不做二次拆分、不改投上一句；`flatTokens` 逐 token 一致（测试 22a） |
| 单句自身已超上限 | 不报错、不切分、原样输出（测试 22d：12s 单 token → 1 句 12s） |

开关：`segmentCaptionTokens(tokens, settings, { mergeCeiling: false })` 或 `SEGMENTER_EXP_C_OFF=1` 可关闭，**仅供对照实验**；不传第三参数 = C 生效。
方案 A 仍为 `ceilingBeforeToken`（默认关闭）；方案 B（`strictContinuationGuard`）已否决，代码保留但注释标明「仅作对照，勿启用」。

### 8.5 新增切点人工抽检（15 处「无源标点切口」全查 + 12 处「源标点后」全查）

C 的 33 个新增切点里，18 处落在源终止标点之后（规则 1，合法）；**15 处落在主循环自己切的位置**（过去被合并 pass 缝掉、现在暴露）。逐条复核结论：

| 判定 | 数量 | 例子 |
|---|---|---|
| **真劈词（主循环既有切口）** | **4** | `テリ｜ちゃん`（「テリちゃん」人名被劈）；`最終｜復`；`なんか｜ラグい`（并补出假问号「え、なんか？」）；`自分｜プラズマ`（「この自分。」还悬空） |
| 语义次优（非劈词） | 3 | `ルミナ｜ルミナ`（重复词分两行）；`、｜プテラ`、`、｜アンブラ`（后句只剩名词） |
| 可接受 | 8 | 切在顿号上（`、｜エレメント`、`、｜夜`、`、｜行け`）或填充词串（`え、な｜な、な…`、`骨、骨｜骨、骨`） |

- 4 处真劈词 **不是 C 新造的切点**：主循环本来就切在那里（守卫 A 只拦 ≤2 字平假名与前缀表命中，`ちゃん`(3 字)、`ラグい`(片假名开头) 都漏判），过去由合并 pass 悄悄缝回去。C 收闸门后它们可见 ⇒ 占比 4/4050 = **0.10%**。
- 已知代价与红线冲突点：角色红线是「宁可漏切不可劈词」，这 4 处属「为了压长句而放弃缝合」的代价。若要同时满足红线，可在闸门上加一条豁免（碎片首 token 命中守卫 A 时仍允许合并），**属行为改动、本轮未做，需拍板**。

### 8.6 方案 A 还需要吗（判断依据）

事实（同一轨实测）：
- C 之后 >7.4s 的 176 句、>13s 的 14 句，**全部来自主循环**（成因 ① 守卫 A 拦长停顿、② 2× 天花板只在并入后检查），合并环节贡献已归零。
- A 只对 13s 尾巴有效：>13s **14 → 2**、最长句 14.28 → 13.11s、最长句字数 60 → 52；>7.4s 只再降 1 句（176 → 175）。
- A 的代价在新口径下依然存在：C+A 的 26 处主循环切口里有 **9 处命中劈词/悬空启发式**（含 4 处悬空宾语行），且最长句仍是 13.11s（>13s）。

判断：**A 不必默认开启**。它买到的只是 13s 尾巴的收敛，代价是「天花板检查绕过守卫」；更干净的做法是把 2× 检查前置到主循环且**仍走守卫**（下一轮议题），而不是启用 A。

### 8.7 风险与未解决项

1. **4 处真劈词**（8.5 节）：主循环既有切口被暴露，占比 0.10%。根因在 v0.2.7 守卫 A 的覆盖边界，非 C 引入的切点；但用户可见。
2. **碎片行 +35（66 → 101）、极短句 +16（437 → 453）、句数 +33（4017 → 4050，+0.8%）**：翻译请求数与缓存 key 随之增加约 0.8%；纯填充词行（`ええ。`/`もう。`/`えっと。`）会独立成行，译文更贴原文但更碎。
3. **最长句只从 14.35s 降到 14.28s**：该句主体是「末 token 自身 2s + 长停顿被守卫 A 拦」，C 按其规格（只做合并上限）无法触及。
4. **>13s 仍有 14 句**：按规格「单句自身已超上限不切分」，只能在主循环侧解决。
5. **口径差异需确认**：规格写的是「字数不得超过 maxCharsPerSentence（28）」，实现里拉丁轨改按词（`maxWordsPerSentence`）——否则 28 字符会把英文轨的合并整体关死（英文一句常态 100+ 字符）。如需严格字面口径，请指示。
6. **闸门拒绝后不做「转投上一句」补救**（规格要求「各自保留为独立句」）；若允许转投，碎片行还能再降，但属行为改动。
